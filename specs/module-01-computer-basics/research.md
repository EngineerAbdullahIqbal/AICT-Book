# Research: Module 1 — Computer Basics (and site foundation)

**Date**: 2026-10-11 | **Plan**: [plan.md](./plan.md)

Every decision below was checked against current documentation through Context7 before it was
written (constitution Principle I). Library IDs used:
`/websites/docusaurus_io`, `/mermaid-js/mermaid`, `/microsoft/playwright`, `/mdn/content`,
`/microsoftdocs/supportarticles-docs`.

## R1. Remove the blog and the sample tutorial (setup task d)

- **Decision**: Use Docusaurus **docs-only mode**: in the classic preset set
  `docs.routeBasePath: '/'` and `blog: false`. Make the book's home page a doc with front matter
  `slug: /`. Delete `src/pages/index.js` (plus its CSS module and the `HomepageFeatures`
  component it uses), `src/pages/markdown-page.mdx`, the `blog/` folder, and the sample
  `docs/tutorial-*` folders. Remove the navbar "Blog" item and the footer links to the blog and
  tutorial.
- **Source**: Docusaurus *Docs Introduction → Docs-only mode*. Warning quoted from docs: "If you
  added `slug: /` to a doc to make it the homepage, you should delete the existing homepage at
  `./src/pages/index.js`, or else there will be two files mapping to the same route!"
- **Rationale**: the site is a book, so the docs are the site. This is the documented way.
- **Alternatives**: keep docs under `/docs/` with a separate landing page; rejected because it
  adds an extra page the teacher must click through.

## R2. Zero broken links, anchors and Markdown links

- **Decision**: keep `onBrokenLinks: 'throw'` (already set). Add `onBrokenAnchors: 'throw'` and
  `markdown.hooks.onBrokenMarkdownLinks: 'throw'`. Then **a passing `npm run build` proves AC-C5**
  with no need to read warnings.
- **Source**: Docusaurus *API → docusaurus.config.js*: `onBrokenLinks` default throws;
  `onBrokenAnchors` default warns; `onBrokenMarkdownLinks` (top-level) is **deprecated in v3.9**
  and replaced by `siteConfig.markdown.hooks.onBrokenMarkdownLinks`. All accept
  `'ignore' | 'log' | 'warn' | 'throw'`.
- **Alternatives**: parse build output for warnings; rejected as fragile.

## R3. Mermaid diagrams (setup task e)

- **Decision**: `npm install --save @docusaurus/theme-mermaid`; add
  `themes: ['@docusaurus/theme-mermaid']` and `markdown: { mermaid: true }`. Set
  `themeConfig.mermaid.theme` to `{light: 'neutral', dark: 'dark'}`. After installing, confirm
  the installed version matches `@docusaurus/core` (3.10.2).
- **Source**: Docusaurus *Markdown Features → Diagrams* and *API → theme-mermaid*. Mermaid
  *Theme Configuration*: `neutral` "is great for black-and-white documents that will be
  printed"; `dark` "goes well with dark-colored elements or dark-mode".
- **Rationale**: neutral prints well and is calm on a projector; dark suits dark mode.
- **Alternatives**: the docs example uses `neutral`/`forest`; `forest` is green-tinted and
  less readable on a dim projector.

## R4. Testing a diagram really rendered (AC-C2, AC-C3)

- **Decision**: the browser test looks for an `svg` with an `aria-roledescription` attribute in
  the page's article. It checks that the SVG contains a non-empty `<title>` (from `accTitle`) and
  a non-empty `<desc>` (from `accDescr`). An un-rendered diagram stays as a code block and has
  no such SVG, so the test fails.
- **Source**: Mermaid *Accessibility*: "The accessible title and description will add `<title>`
  and `<desc>` elements within the SVG element and the aria-labelledby and aria-describedby
  attributes in the SVG tag." "Mermaid automatically adds … aria-roledescription".
- **Rationale**: one browser check proves both "drawn as a picture" and "accessible".

## R5. Sidebar with 16 modules (setup task f)

- **Decision**: keep the autogenerated sidebar (`{type: 'autogenerated', dirName: '.'}`), with
  one folder per module under `docs/`. Each folder has a `_category_.json` (`label`,
  `position`) and an `index.md` module overview page. By the category index convention it
  becomes the category's own page. Lessons set their order with `sidebar_position`. Rename the
  sidebar id from `tutorialSidebar` to `bookSidebar`.
- **Source**: Docusaurus *Sidebar → Autogenerated*: "each folder creates a sidebar category,
  and each file creates a doc link"; category index convention: "Named as `index`
  (case-insensitive): `docs/Guides/index.md`"; `_category_.json` fields `position`, `label`;
  front matter `sidebar_position`.
- **Note from the docs**: "If a folder only has one index page, it will be turned into a link
  instead of a category." So Modules 2–16, which have only their placeholder `index.md` for
  now, will show as **links**, not expandable categories. They become categories when their
  lessons are added. The test for BK-01 checks the 16 module labels in order, which works for
  both.
- **Alternatives**: a hand-written `sidebars.js`; rejected because it must be edited for every
  new lesson.

## R6. Windows 10 and Windows 11 steps on one page

- **Decision**: where steps differ, use `<Tabs groupId="windows-version">` with
  `<TabItem value="win10" label="Windows 10">` and `<TabItem value="win11" label="Windows 11">`.
  Same `groupId` means picking "Windows 11" once switches every tab group on the page and is
  remembered.
- **Source**: Docusaurus *Markdown Features → Tabs*: "Two Tabs components with the same
  groupId … sync their selected tab … and the choice is persisted in localStorage."
- **Rationale**: the teacher picks the version of the lab computer once; the page stays tidy.
- **Alternatives**: two separate lists one after another; rejected as long and easy to mix up.

## R7. UNVERIFIED marker

- **Decision**: `:::warning[UNVERIFIED]` … `:::`, as defined in `specs/constitution.md`
  Section 4.
- **Source**: Docusaurus *Markdown Features → Admonitions* (types `note`, `tip`, `info`,
  `warning`, `danger`; custom title with square brackets).

## R8. Urdu help text

- **Decision**: wrap every Urdu phrase in `<span lang="ur" dir="rtl">…</span>` (lesson files are
  `.mdx`, which allows HTML/JSX). Add a `:lang(ur)` rule in `src/css/custom.css` for a slightly
  larger size and line height. **No web font is added now.** The page uses the fonts already on
  the computer. The owner checks how Urdu looks on the Windows 11 laptop and projector
  (quickstart step 6). A font is added only if that check fails, after checking its docs.
- **Source**: MDN *Global attributes → lang* ("Use the lang attribute on an inline element such
  as `<span>` to mark phrases written in a different language") and *→ dir* (`rtl`).
  Docusaurus *Styling and Layout → Global styles* (`customCss`) and *API → stylesheets* (for a
  font later, if needed).
- **Alternatives**: a whole Urdu locale via i18n; rejected because translations are out of
  scope.

## R9. Automated tests (Playwright)

- **Decision**:
  - Install: `npm i -D @playwright/test`, then `npx playwright install chromium`. If Ubuntu is
    missing system libraries, the owner runs `npx playwright install --with-deps chromium`
    (it asks for the sudo password, so Claude does not run it).
  - `playwright.config.js` in `aict-guide/`, tests in `aict-guide/tests/`, Chromium only.
  - `webServer`: `command: 'npm run build && npm run serve -- --port 3100 --no-open'`,
    `url: 'http://localhost:3100'`, `reuseExistingServer: false`, `timeout` long enough for a
    build. Port 3100 so tests never collide with the dev server on 3000. Tests always run
    against a fresh **production build**, so every test run is also a broken-link check.
  - npm scripts: `"test": "playwright test"`.
- **Sources**: Playwright *Installation / CI* (`npm i -D @playwright/test`,
  `npx playwright install --with-deps`) and *Configuring a web server* (`command`, `url`,
  `reuseExistingServer`, `timeout`, default 60000 ms; `url` is passed as `baseURL`). Docusaurus
  *CLI → serve* (`--port`, default 3000; `--no-open`).
- **Alternatives**: test against `npm run start` (dev server); rejected because broken-link
  checks only run in a production build (Docusaurus docs: "The broken links detection is only
  available for a production build").

## R10. Verifying lesson facts (Windows, Paint, Recycle Bin)

- **Finding**: Context7's Microsoft library (`/microsoftdocs/supportarticles-docs`) covers
  IT-admin troubleshooting (for example `shutdown /s /t 0`), not end-user how-to pages.
- **Decision**: for Module 1 software steps, use Microsoft's official end-user support pages
  (support.microsoft.com), fetched and quoted at writing time, and listed in each lesson's
  Sources. Context7 is still checked first for every claim. Anything not confirmed by an
  official page is marked UNVERIFIED.
- **Rationale**: matches `specs/constitution.md` Section 3: Context7 first, then the maker's
  official documentation.
